# ngrep design

ngrep is a local search CLI. `index` walks a tree and writes a trigram inverted index. `search` intersects those postings and then reads candidate files to print path, line, and column. `watch` rebuilds that index when the tree changes. Nothing leaves the machine.

The on-disk layout is specified in [docs/index-format.md](docs/index-format.md). This note covers the commands, ignore rules, and library choices.

## Commands

| Command | Behavior |
| --- | --- |
| `ngrep index <path>` | Walk `<path>`, update `<path>/.ngrep/index` (or `--index`). Prints English progress on stderr (`added:`, `updated:`, `removed:`, and a periodic `indexed` summary). `-q` / `--quiet` silences that progress. Exit 0 on success. |
| `ngrep <pattern> [PATH...]` | Same as `search`. The words `index`, `search`, and `watch` are subcommands; `ngrep -- index` searches for the pattern `index`. No path searches `.`. |
| `ngrep search <pattern> [PATH...]` | Query an index discovered by walking parents for `.ngrep/index`, once per path. A `.netgrep` directory is not discovered. If none exists, `--scan` is set, `--no-ignore` / `--no-ignore-vcs` is set, `-L` / `--follow` is set, the path is outside the indexed root, the path is inside the root but absent from the snapshot, or the path is inside the root and the pattern is not trigram-safe, scan file contents. Each path has its own ignore stack and its own index lookup. |
| `ngrep watch <path>` | Build an index, then watch the tree with `FileSystemWatcher`. Events are debounced (300 ms) into one incremental `index` pass. Those builds do not print index progress. A pass stats every file and reads only files whose size or mtime changed, then writes the index in chunks (4096 paths or 32 MiB of changed bytes). Writes under the index directory, `<root>/.ngrep`, and `<root>/.git` do not retrigger a build. Ctrl+C stops the process with exit 0. |

`index` progress goes to stderr and is not part of `--format`. A new file is `added: path`, a changed file is `updated: path`, and a stale document is `removed: path` (removals are ordered by path). Unchanged and skipped files are counted in a summary every 100 examined files and once at the end: `indexed 120/500, added 3, updated 1, unchanged 116, removed 0, skipped 0`. The summary is skipped at a multiple of 100 when that count is the whole walk, so the final line is not printed twice. `skipped` there is binary, too large, and unreadable. Ignored files are omitted from the walk. `-q` / `--quiet` on `index` silences the progress. Search `-q` / `--quiet` / `--silent` is a different option and suppresses the match report. `watch` calls the indexer with progress off.

Each commit rewrites the index into `<index>.tmp` and replaces the live directory only after the three v1 files are complete. Readers never open `.tmp`. If the replace has not happened, they open `<index>` or, when that directory was already renamed aside, `<index>.bak`. `ngrep index` and `watch` keep the postings and document table in memory (that is the index) and commit a full snapshot in chunks, not once per file. A chunk closes after 4096 added, updated, or removed paths, or after 32 MiB of raw bytes from those adds and updates, whichever comes first. The closing commit still runs so `updatedUtc` moves. Path lines for a chunk are printed only after that chunk's commit succeeds. The every-100 summary is the in-memory walk and can appear before the next chunk commit. A crash keeps the last successful chunk: earlier path-ordered files are searchable, later ones are not, and removals that have not been committed remain. A caller that passes a persistence callback still commits each added, updated, or removed path before the callback returns, then commits once more. Unchanged size and mtime, and a matching hash, are stored in the next chunk rather than one commit per file.

Decoded file text is not kept. At most `workers × 4` files are being read (the parallel window). Each file is at most 32 MiB, so that window is at most a few dozen buffers, not the tree. Between commits the only extra dirty state is the progress lines for the open chunk (at most 4096 paths) and the document rows already merged into the index. After a commit, cached ndjson lines are dropped. The resident set is therefore about one index (paths, hashes, line starts, posting lists) plus one chunk, not one copy of every file. Posting lists are the large part: about 4 bytes per distinct trigram per file, with list slack. A cold build of 100,000 tiny files (a short unique prefix plus one shared line) peaked near 270 MB RSS and finished in about 6 seconds on a 4-CPU Linux box. That cost scales with the index, not with an extra buffered copy of the tree.

Index reads use the same `RandomAccess.ReadAsync` reader as search. The first buffer is 8 KiB, so a NUL in that window stops the read; a text file is then read in full or mapped at 256 KiB. Workers default to the processor count. `NGREP_THREADS` overrides that, and `NETGREP_THREADS` is used only when `NGREP_THREADS` is unset. With one worker the caller reads the files. With more, background threads read and the caller applies ids and path lines in path order.

Shared options: `--format text|json|ndjson|rgjson`, `--index <dir>`. `rgjson` is search-only; `index` and `watch` exit 2 if it is set. Search also has `--ignore-case` / `-i`, `--smart-case` / `-S`, `--case-sensitive`, `-E` / `--extended-regexp` / `--regex` (.NET regex, the default; not POSIX BRE or ERE, and not ripgrep's `-E` encoding), `-F` / `--fixed-strings` (literal text; exit 2 with `-E` or `-P`), `--scan`, `--no-ignore`, `--no-ignore-vcs`, `--hidden`, `--binary`, `-u` / `--unrestricted` (repeat up to three times), `--files`, `-e` / `--regexp` (repeatable, OR), `-f` / `--file` (pattern files, OR), `-w` / `--word-regexp`, `-x` / `--line-regexp`, `-v` / `--invert-match`, `-l` / `--files-with-matches`, `--files-without-match`, `-c` / `--count`, `-q` / `--quiet` / `--silent`, `-n` / `--line-number` (on by default), `-N` / `--no-line-number`, `--column` (on by default), `--no-column`, `--vimgrep`, `-0` / `--null`, `-r` / `--replace` (print-only; `-F` inserts the text literally, regex mode expands captures), `-s` / `--no-messages`, `-o` / `--only-matching`, `--heading`, `--no-heading`, `--stats`, `-g` / `--glob`, `-t` / `--type`, `-T` / `--type-not`, `--type-add`, `--type-list`, `-A` / `-B` / `-C`, `-U` / `--multiline`, `--multiline-dotall`, `--color auto|always|never`, `-j` / `--threads`, `-d` / `--max-depth` (`--maxdepth`), and `-L` / `--follow`. `-N`, `--column`, `--no-column`, `--vimgrep`, `-0`, and `-r` change text output only. `--files` still honors `-0`.

`-e` values are patterns. `-f` values are pattern files. A positional token that appears before the first `-e` or `-f` is also a pattern. Any other positional is a path. Several paths are searched in order. No path searches `.`. With two or more paths, printed paths are prefixed with the path that was named (`.` is not). A missing path is still exit 2; the other paths are still searched. The default pattern language is .NET regular expressions (non-backtracking), the same engine as `-E` / `--regex` / `--extended-regexp`. Those flags are aliases of the default. `-F` selects literal text and cannot be combined with `-E` or `-P`. `-w` checks both ends of the match: a boundary is a transition between a word character (Unicode letter, digit, or `_`) and a non-word character, or either end of the text. `-x` requires the whole line. Line text drops a trailing CR. A literal must equal that text. A regex is `\A(?:pattern)\z` on that text, so the original pattern is what trigram extraction sees. `-v` emits every real line that contains no hit. A trailing newline is not an extra line, and an empty file has no lines. `column` is 1 and `text` is the line. `-n` is the default and `-N` drops the line number. `--no-column` drops the column. `--vimgrep` forces `path:line:column:text` and no heading. `-0` writes NUL after each printed path, including `--files`. `-r` rewrites printed matches and does not edit files; the default regex expands captures, `-F` inserts the replacement literally, and `-v` lines are left as read. `-s` hides `Path not found` and `Unreadable` for a path the user named; the exit code is still 2. Walk-time unreadable files stay skipped. `-q` writes no match report and is mutually exclusive with `-c`, `-l`, and `--files-without-match`.

Boolean short options may be clustered (`-nEi`, `-uu`, `-iS`). A value short ends the cluster and takes the rest of the token with `=` (`-nEepat`). A token that already starts with a value short is not rewritten. After `--`, tokens stay literal. `-u` / `--unrestricted` is counted before parse and rewritten, up to three times: `-u` adds `--no-ignore` (every ignore file, including `.ignore` and `.rgignore`), `-uu` also `--hidden`, `-uuu` also `--binary`. A fourth use exits 2. `.git`, `.ngrep`, the index directory, and symlinks stay skipped.

`--files` prints the walk a content scan would open, one relative path per line, with no pattern. Ignore, hidden, glob, and type filters apply. It does not read bytes, so NUL files and files over 32 MiB are listed, and `-uu` and `-uuu` list the same paths. It does not use the index. `--format` is ignored. `-0` / `--null` follows each path with NUL and no newline. Exit 0 if any path is listed, 1 if none, 2 on error. `-q` suppresses the lines and keeps that code. `-e`, `-f`, `-l`, `--files-without-match`, and `-c` exit 2.

`--binary` searches a file with a NUL in the first 8 KiB and prints the match as text. Ripgrep's `--binary` prints a warning and not the line. The 32 MiB cap stays. The index omits those files, so the search scans.

`-S` / `--smart-case` folds a pattern only when its text contains no uppercase letter (`char.IsUpper`). Each pattern is separate. `-i` folds every pattern. `--case-sensitive` folds none. The last of those three wins. `-s` stays `--no-messages`.

`NGREP_CONFIG_PATH` is a search config file: one argument per line, `#` comments and blank lines ignored, prepended before the command-line arguments (after an explicit `search` token). `index`, `watch`, `--help`, and `--version` do not read it. `RIPGREP_CONFIG_PATH` is not read. An unknown flag or an unreadable file exits 2 and names `NGREP_CONFIG_PATH`. The last `--format`, `--index`, `--color`, `-A`, `-B`, `-C`, and `-j` wins.

`-l`, `--files-without-match`, `-c`, and `-q` select a report. More than one is exit 2. `-l` keeps the first hit in each file (leftmost index, or the first whole line when `-x` is set) and prints paths, unless `--stats` is set, in which case every hit is collected so the stderr line count is complete and the path list is unchanged. `--files-without-match` prints searched paths with no hit. When the trigram prefilter is safe, documents that miss the required literal are paths without a match and are not read. `-c` counts distinct matching lines per file and omits zeros. `-q` prints nothing on stdout and uses the same per-file stop as `-l` unless `--stats` is set. `-v` inverts the hit before that report: a file of only matching lines is a `--files-without-match` hit, and `-c -v` counts the other lines. Exit 0/1 follows whether that report was non-empty (`-q` included; its stdout stays empty). `-o` replaces `lineText` with `text` in text output only. Machine match objects are not renamed.

`-f` / `--file` appends patterns after positional and `-e` patterns. Each file is one pattern per line. The newline is not part of the pattern. An empty line matches every line (one hit per line at column 1). A line starting with `#` is that pattern, not a comment. `\#` is kept as written. The default regex treats `\#` as an escape, so it matches `#`. `-F` keeps the backslash literal. `-E` / `--regex` matches the default. `-` reads patterns from stdin, not the haystack. A missing path is exit 2. A zero-length file with no other pattern is exit 2. A positional before the first `-e` or `-f` is a pattern; after either flag, positionals are paths, so `ngrep -f pats.txt index` searches the path `index` and `ngrep -e foo src tests` searches both directories.

Content stdin is a different input. `ngrep <pattern> -` reads the haystack from stdin even when stdin is a terminal. With no path, stdin is the haystack only when it is not a terminal (`Console.IsInputRedirected`) and `-f -` was not used; a terminal still searches `.`. An explicit path, including `.`, is that path and leaves stdin unread, so a pipe can feed something else while the tree is searched. The path `-` is never a file named `-`; that file is `./-`. Several other paths are still searched in order; a `-` among them is stdin and the rest are roots. `-f -` already consumed stdin, so a missing path stays `.`, and a path of `-` exits 2 (`attempted to read patterns from stdin while also searching stdin`). A second `-f -` exits 2 (`error reading -f/--file from stdin: stdin has already been consumed`). `ngrep -f pats.txt -` reads patterns from the file and bytes from stdin.

The match path is `(standard input)` (ripgrep prints `<stdin>` and omits it unless `-H`; ngrep has no `-H` and keeps the path on a single input). Text is `(standard input):line:column:text`. `--heading` prints the name once and `line:column:text` below it. JSON, NDJSON, and rgjson use the same path string. `-l` prints the name. `-c` prints `(standard input):count`. The stream is one file: no index, no scan note, no glob, type, or ignore filter. A NUL in the first 8 KiB, or more than 32 MiB, is the same skip as a file (exit 1, not an error). `--binary` searches that stream the way it searches a file. A read error exits 2 (`Unreadable: (standard input)`); `-s` hides the line. Empty stdin has no lines. `--stats` counts the stream when its bytes were examined. The read is the file reader without a map: pooled chunks, the NUL probe, and the same early stop for `-l` / `-q`.

Text headings: when stdout is a terminal and more than one file’s contents were read, match lines drop the path prefix and a path heading is printed first, with a blank line between files. `--heading` forces that. `--no-heading` keeps `path:line:column:text` and wins if both are set. `--vimgrep` also forces the prefixed form, with line numbers and columns. JSON, NDJSON, and rgjson ignore both flags. Column stays in the heading form (`line:column:text`) unless `--no-column` is set. `-N` drops the line number from that form.

`--stats` writes five lines to stderr after stdout: files searched, files matched, lines matched, matches, elapsed ms. Files searched are files whose bytes were examined. Prefilter drops, binary files, oversized files, and unreadable files are omitted. The numbers are pattern hits, including when the stdout report is `--files-without-match`.

`--color` defaults to `auto`. Color is applied only for `OutputFormat.Text`. `auto` is on when stdout is a terminal, `NO_COLOR` is empty, and `TERM` is not `dumb`. Tests replace `Console.Out`, which counts as not a terminal.

Regex options are `CultureInvariant` and `Multiline` (line anchors), plus `IgnoreCase` and, for `--multiline-dotall`, `Singleline`. Never `Compiled`. Without `-U` / dotall, a match whose span contains `\n` is discarded. With them, the span is kept. `line` / `column` / `lineText` stay on the first line; `text` is the whole slice. `-v` marks every overlapped line. `-U` does not change a non-regex substring search.

Globs follow gitignore syntax via the same interpreter regexes (no `RegexOptions.Compiled`). A leading `!` excludes. With at least one include glob, paths start excluded. The last matching glob wins. `-t` names are OR; `-T` names are excluded after that. `--type-add name:*.a,*.b` appends globs (bare `ext` means `*.ext`). Filters run after gitignore. They never re-include an ignored path, including when the query uses the index (ignored files were not indexed). `--no-ignore` skips every ignore file. `--no-ignore-vcs` skips `.gitignore`, `info/exclude`, and the global excludes file, and still reads `.ignore` and `.rgignore`. Both force a content scan, because the index was built with every source and has no ignored documents. `.git`, `.ngrep`, and the index directory are still skipped. Symlinks are still skipped unless `-L` / `--follow`. `--type-list` prints `name: *.ext, ...` and exits 0.

Context is stored on the match as optional `before` / `after` arrays and is omitted from JSON when the user did not ask for it. Text context lines are `path-line-text`, or `line-text` under a heading. Groups that are not contiguous are split with `--`. A line that is both context and a match is printed once, as a match.

Exit codes stay 0 / 1 / 2. `--type-list` is 0. `--files` is 0 when it lists a path and 1 when it lists none. A fourth `-u` is 2. A canceled search is 2 (`search canceled` on stderr).

`search` paths in the output are relative to the **index root** when an index is used (so `search ngrep src` still prints `src/App.cs`). A content scan prints paths relative to the directory that was scanned. Separators are `/`. Globs and types are matched against that same relative path, not against a display prefix. A path the user passed is searched even when that path is hidden. Components under it that start with `.` still need `--hidden`. When more than one path is given, each result is prefixed with the path argument (except `.`) so the same file name in two roots stays distinct. Ignore rules and index discovery still run per root.

`--format rgjson` writes one JSON object per line with `type` of `begin`, `context`, `match`, `end`, or `summary`. `context` is emitted only when context was requested. `absolute_offset` is the UTF-16 index of the line start in the decoded text. `summary.data.stats.elapsed_ms` is wall time. Match field names inside `--format json` / `ndjson` stay `path`, `line`, `column`, `text`, `lineText`. `rgjson` is not that object, and those objects do not gain `absolute_offset`.

`watch` is a stream. `--format json` and `--format ndjson` both emit one object per event (`ready`, `reindexed`, `stopped`) so a long-running process does not buffer a single array. `index --format json` is one object. `search --format json` is `{"matches":[...]}`. `search --format ndjson` is one match per line and nothing else. Diagnostics go to stderr. Field names for a match are `path`, `line`, `column`, `text`, `lineText`, in that order. `line` and `column` are 1-based. Context adds `before` and `after` after those fields, each an array of `{line, text}`, only when context was requested.

Exit codes: `0` success (index or watch finished, or search found a match), `1` search ran and found nothing, `2` usage or runtime error. Parse errors are plain text on stderr in every format.

## Confirmation

After the candidate set is known, ngrep reads file bytes on task workers and searches each file independently. `-j` / `--threads` wins when it is set. Otherwise `NGREP_THREADS`, otherwise `NETGREP_THREADS` when the new name is unset, otherwise `Environment.ProcessorCount`. `SearchQuery.MaxDegreeOfParallelism` is that width (`0` means the environment default). One worker, or a single candidate file from an index, stays sequential. The outcome records `Confirmation` of `parallel` or `sequential` and the worker count. Those fields are not machine output.

`-d` / `--max-depth` caps how far a directory walk descends. Depth 0 is the start path. A directory at depth 0 is not listed, so `-d 0` on a directory yields no files; `-d 0` on a file still reads that file. Depth 1 is an immediate child. A directory is listed only when its depth is less than the cap, which is what keeps `.gitignore` files past the cap unread. Ignore rules, hidden names, and `--no-ignore` are otherwise unchanged. An indexed search applies the same depth to document paths and does not open anything deeper. The index stays in use when it already covers the path.

A content scan lists directories and reads files at the same time. Hits are printed when that file is confirmed. The scan does not collect or sort the tree before the first read. With one worker the walk is depth-first (entries sorted by name, files in a directory before its subdirectories). With more workers, several tasks list sibling directories and the read pool is still `-j` (otherwise the same default). Those hits print in completion order, not global path order. On Linux the listing is `readdir` and uses the directory entry type, so regular files and directories are not `lstat`ed; an unknown type falls back to attributes. Other systems take attributes from `FileSystemInfo` during that listing. Symlinks are still not followed unless `-L` / `--follow`. Index confirmation still feeds the candidate list to the task pool and emits in path order. Each worker reads with `RandomAccess.ReadAsync`. The process entry point awaits that pipeline. `-q` without `--stats` stops the walk at the first matching file. `-l` still visits every file and stops reading a file once the matching line is buffered. `--stats` reads each file to the end. The first Ctrl+C cancels the invocation token (and `Console.CancelKeyPress`) and exits 2 (`search canceled`). The walk stops queuing directories and readers stop at the next chunk. The token is not passed into `RandomAccess.ReadAsync`, because cancel there calls `CancelIoEx` and that races the Windows overlapped dispose. A second Ctrl+C exits the process immediately with code 2.

Each candidate is read asynchronously. `File.OpenHandle` uses `FileOptions.Asynchronous` and `FileOptions.SequentialScan`, and `RandomAccess.ReadAsync` fills an `ArrayPool` buffer (64 KiB to start, grown to the file length, 32 MiB cap). A NUL in the first 8 KiB marks the file binary (`IndexOf(0)`, a memchr). The length is queried only after the first buffer comes back full, so a short file avoids an extra stat. A file of at least 256 KiB is memory-mapped once that length is known; a map has no async form. The buffer is returned before line matching. At startup the thread-pool minimum is at least two workers per processor so those reads are not waiting on thread injection. When the query is not inverted and every alternative has an ASCII required piece, a file that misses those bytes is dropped before UTF-8 decode. That applies to short literals too. The check is a SIMD scan of the pooled bytes: AVX-512BW loads 64 bytes, AVX2 loads 32, SSE2 or Vector128 loads 16, and a scalar loop covers the tail and machines without those ISAs. `Avx512BW.IsSupported` is tested first, so a CPU without AVX-512 never executes that path. One literal nominates alignments where the first byte, the rarest interior byte, and the last byte match, then an exact compare accepts whatever those bytes do not already cover. Two or more literals of length at least 2 use a Teddy nibble fingerprint: each pattern owns a bit, a shuffle tests the first two or three bytes, and an exact compare confirms the candidate. Shorter disjunctions still nominate distinct first bytes. An alternation that needs every piece (`foo.*bar`) scans each ASCII piece and keeps the file only when all of them hit. `--ignore-case` folds ASCII `A-Z` in that compare and does not fold other bytes. Non-ASCII pieces are confirmed on the decoded string. An ASCII file whose patterns are ASCII literals is confirmed on the bytes themselves: line and column follow the byte offsets, and only matching lines (plus context) are turned into strings. `-l` without context stops reading once that matching line is in the buffer. A file with a non-ASCII byte still takes the UTF-8 decode path so columns stay UTF-16 indexes.

Trigram selection uses the same required literals. Clauses are OR; parts inside a clause are AND. Adjacent exact literals are concatenated (`(?:foo|bar)baz` requires `foobaz` or `barbaz`). A `*` / `?` / `{0,…}` gap is not concatenated (`foo.*bar` requires `foo` and `bar`, not `foobar`). A repeat of one exact literal uses the minimum copy (`(ab){2}` requires `abab`). A repeat of several alternatives only requires one of them (`(foo|bar){2}` requires `foo` or `bar`). Each part of length ≥ 3 contributes its trigrams; shorter parts do not. If any clause has no such part, or extraction fails (lookaround, backreferences, more than 64 clauses), every indexed document is a candidate when the search path is the indexed root. The same query under a subdirectory of that root scans the subdirectory, because the snapshot is not the walk. A trigram-safe query scans too when the path has no document row. `-v` never selects on trigrams: lines that do not match are the result, including files the pattern misses. Invert still uses the worker pool and stops scanning a line after its first hit. `-w` keeps the prefilter and checks boundaries at confirm time. `SearchOutcome.UsedTrigramPrefilter` records whether the posting intersection ran. It is not machine output.

Line starts on the decoded text use the same dispatch, looking for UTF-16 `\n` 32, 16, or 8 chars at a time. That map is what `line` / `column` come from. It is not a UTF-8 memchr over the file bytes.

`RegexOptions.Compiled` is not used, because AOT cannot compile a user pattern. The default engine is `RegexOptions.NonBacktracking` (the same engine `-E` selects): a linear automaton that does not emit IL, so it stays on the Native AOT path. It does not support backreferences, lookaround, or atomic groups. Those patterns exit 2 with a message that names `-P` / `--pcre`, which selects the existing backtracking interpreter (five-second match timeout). A case-sensitive regex that is only a literal is still searched as that literal. Other ASCII patterns that the in-tree compiler recognizes (a literal, a literal alternation, a single character-class run, a literal prefix plus classes that do not need backtracking, or a Thompson NFA run as a Pike VM) are confirmed on the file bytes. That scan is linear. Patterns it does not recognize, and any non-ASCII file, use `NonBacktracking` on the decoded string. When every alternative has an ASCII literal of at least two characters and the match cannot cross lines, a file that misses the literal is not decoded. Files at least 256 KiB are mapped rather than copied, so a warm miss is a scan of the page cache. The JIT keeps a real `IsSupported` check, so AVX-512 runs only on CPUs that have AVX-512BW. Default Native AOT for `linux-x64` folds AVX2 and AVX-512 off (baseline x86-64-v2) and emits the SSE2 / SSSE3 scan, which does not fault on a CPU without AVX-512. `x86-64-v3` is the opt-in that makes AVX2 required. `x86-64-v4` makes AVX-512 required; the project does not set it.

## Ignore rules

Indexing and content scan share one walker.

Hard skips, even if a gitignore negation, `--hidden`, `--no-ignore`, `--binary`, or `-uuu` would bring them back:

- any directory named `.git` or `.ngrep` (including when that directory is the path you passed)
- the index directory, when it sits inside the walk
- symlinks, unless search was given `-L` / `--follow` (`index` and `watch` never follow)

Then hidden names, unless `--hidden` or the walk root is that path:

- a file or directory whose name starts with `.` is not searched
- on Windows and macOS, the file-system hidden attribute is hidden too, so a content scan does not descend into `AppData`
- `.gitignore`, `.ignore`, and `.rgignore` are still loaded when their directory is entered
- the index walk passes `includeHidden: true`, so those files are stored. An indexed search still treats hidden as a dot name only, because the snapshot does not record the attribute
- `-g` and a gitignore `!` rule do not un-hide a path

Then ignore files. The first source that matches a path decides, highest precedence first. Within one source, a more nested file wins, and within one file the last matching pattern wins. A whitelist in a lower source does not bring a path back.

Sources, highest precedence first:

- `.rgignore`
- `.ignore`
- `.gitignore`
- `$GIT_DIR/info/exclude` (the common git dir when `.git` is a `gitdir:` file and `commondir` is present)
- the global excludes file

`.gitignore`, `.ignore`, and `.rgignore` are read from the git root down to the file. The walk root's own files are read when that directory is listed. Patterns match the path relative to the file that defined them. A rule in `src/.gitignore` does not affect the repo root. If there is no git root, only those files at the walk root and below apply. ngrep does not read `.ignore` above the git root. Ripgrep walks those parents to the filesystem root. `.gitignore` is still read outside a checkout. Ripgrep skips `.gitignore`, `info/exclude`, and the global file unless it finds a repository.

`info/exclude` and the global file apply only when a `.git` file or directory is found. Their patterns are relative to that git root. Ripgrep anchors the global file at the process working directory.

The global path is `core.excludesFile`, read from git config without starting git: `/etc/gitconfig` on Unix (unless `GIT_CONFIG_NOSYSTEM` is set; `GIT_CONFIG_SYSTEM` replaces it), then `$XDG_CONFIG_HOME/git/config` or `~/.config/git/config`, then `~/.gitconfig` (`GIT_CONFIG_GLOBAL` replaces those two), then `$GIT_DIR/config`. Later files win. `include.path` is followed (`~` and a path relative to the including file). `includeIf` is not. A leading `~` expands to the home directory. A relative `core.excludesFile` is relative to the process working directory. When the key is unset, the default is `$XDG_CONFIG_HOME/git/ignore`, or `~/.config/git/ignore` when `XDG_CONFIG_HOME` is unset. A missing file adds no rules.

The pattern language is the same in every source. `!` negates. A trailing `/` matches only directories. A pattern with no `/` matches in any directory. A leading `/` or an internal `/` anchors it to that file's directory (or to the git root, for `info/exclude` and the global file). Globs: `*` and `?` do not cross `/`. `**` crosses directories. `[abc]` and `[!abc]` work. If a parent directory is ignored, everything under it is ignored. `build/` plus `!build/keep.txt` does **not** bring `keep.txt` back. `build/*` plus `!build/keep.txt` does, because the directory itself is not ignored. This matches git 2.43.

`--no-ignore-vcs` skips `.gitignore`, `info/exclude`, and the global file. `.ignore` and `.rgignore` still apply. `--no-ignore` skips every ignore file. Both scan instead of using the index. `-u` is `--no-ignore`, so it skips `.ignore` and `.rgignore` as well as the git sources.

Binary files (a `NUL` in the first 8192 bytes) and files over 32 MiB are not indexed. `--binary` and the third `-u` search those NUL files as text and force a content scan. The 32 MiB cap stays.

## Libraries

- **System.CommandLine 2.0.12** defines `index`, `search`, and `watch`. A leading positional that is not one of those words is rewritten to `search`, so `ngrep <pattern> [PATH...]` works. Handlers take `ParseResult` and call `GetValue`, which stays on the trim-safe 2.0 API (no reflection-based model binding). `string[]` options collect repeated flags; the search binder walks tokens so `-e` values are not mistaken for paths.
- **`FileSystemWatcher`** is the watch backend. It is in the shared framework and works with Native AOT. The MVP does not coalesce bursts beyond a 300 ms flag, and it does not raise the inotify watch limit.
- **Gitignore is in-tree.** [MAB.DotIgnore](https://github.com/markashleybell/MAB.DotIgnore) is the usual NuGet parser, and it compiles every pattern with `RegexOptions.Compiled`, which Native AOT cannot generate. It also merges rules into one list, so a nested `*.log` would leak out of its directory. ngrep matches common gitignore globs with an in-tree interpreter (no `RegexOptions.Compiled`). A pattern whose character class that interpreter does not handle, or a match that exceeds its step limit, falls back to the regex interpreter (`RegexOptions.CultureInvariant`). Each file's rules stay on the stack for that source.

JSON is written with `Utf8JsonWriter` and read with `JsonDocument`. `JsonSerializer` reflection is disabled in the project file. Regex search does not use `RegexOptions.Compiled` and not a source-generated pattern (the pattern is user input). The default is `RegexOptions.NonBacktracking` (linear, AOT-safe, no backreferences or lookaround). `-P` / `--pcre` keeps the backtracking interpreter, with a five-second timeout. `RegexOptions.Multiline` and `Singleline` stay on both engines. Gitignore globs stay on the interpreter.

## Native AOT

The executable targets `net11.0`, sets `PublishAot`, `InvariantGlobalization`, and turns off reflection-based JSON, EventSource, and metadata updates. Case folding is invariant lowercase, which is what the index stores. Culture-specific casing is intentionally unavailable.

Search always uses that async pipeline in the Native AOT binary. Workers are tasks, file bytes come from `RandomAccess.ReadAsync`, and confirm still uses the synchronous SIMD literal scan and byte automaton. There is no synchronous search-read path and no switch to turn async off. The async APIs are shared-framework types (`Task`, `Channel`, `RandomAccess`) with no reflection and no `RegexOptions.Compiled`, so Native AOT compiles them into the one binary. `Main` returns `Task<int>` and the search command is an async handler awaited by `ParseResult.InvokeAsync`.

`dotnet build` and `dotnet test` stay on the JIT. `dotnet publish -c Release` produces the native binary. Remaining gaps are listed in the README after that publish.
